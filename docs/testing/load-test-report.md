# Звіт про навантажувальне тестування

| Атрибут | Значення |
| --- | --- |
| Об'єкт | Wargame Broker, REST API брокера |
| Дата | 16.11.2026 |
| Інструмент | Apache JMeter 5.6.3 (Docker-образ `alpine/jmeter:5.6.3`), сценарій [load-tests/broker-load.jmx](../../load-tests/broker-load.jmx) |
| Середовище | Ubuntu, ядро Linux 7.0; Docker 29.9; стек `docker compose up -d` (postgres, backend з лімітом 512 MiB, dashboard), без симуляторів |
| Пов'язані вимоги | NFR-5 (складність туману війни), NFR-6 (обмеження пам'яті), FR-8 (скидання) |

## Мета

Перевірити, що брокер витримує тривалий бій із великою кількістю юнітів, поки дашборди опитують стан. Під час тесту вимірювалися затримки кожного ендпоінта, частка помилок і споживання пам'яті та процесора контейнером backend.

## Профіль навантаження

| Група потоків | Потоків | Що робить |
| --- | --- | --- |
| Prepare session | 1, одноразово | `reset`, `init`, реєстрація Blue і Red |
| Tick driver | 1 | без пауз грає тіки: `submit` Blue → `submit` Red → `fog-of-war` Blue; кожна сторона має 100 юнітів типу INFANTRY з радіусом огляду 50 на полі 300 × 200 |
| Observers | 20 | імітують дашборди: `status`, `state/full`, `state/events` з паузою 300–700 мс |

Тривалість — 120 с. Кожен 5-й тік брокер записує snapshot зі 200 юнітів (`snapshot-interval: 5`). Перевірка відповіді — код 200 для всіх запитів.

Запуск:

```bash
DURATION=120 OBSERVERS=20 UNITS=100 load-tests/run-load-test.sh
```

Скрипт зберігає в `load-tests/results/<час>` сирі результати (`results.jtl`), HTML-звіт JMeter (`report/index.html`) і заміри `docker stats` контейнера backend кожні 2 с (`backend-resources.csv`).

Прогін на остаточній версії (коміт f9e8c4c): зіграно 14 905 тіків, 49 404 запити, **0 помилок**, 410 запитів/с.

`submit` від Red повільніший, ніж від Blue, бо другий хід закриває бар'єр. На ньому брокер рахує туман війни для обох сторін (100 × 100 пар юнітів), переводить сесію на наступний тік і кожен 5-й раз пише snapshot у PostgreSQL. Розрахунок видимості окремо (`fog-of-war`) займає менше 1 мс, що узгоджується з NFR-5.

Базовий прогін на коміті 91a4d90 (до виправлення BR-10) дав близькі показники: 40 049 запитів, 0 помилок, `submit` Red у середньому 8,1 мс (p99 118 мс), пам'ять 274–311 MiB.

## Знайдений дефект

Після тесту в БД залишилося близько 2 400 snapshot'ів і 470 000 рядків юнітів. Скидання симуляції на цій історії тривало **105 с**, і весь цей час брокер не приймав ходи нового бою. Дефект оформлено як [BR-10](bug-reports/BR-10.md).

| Версія | Обсяг історії | Час `POST reset` |
| --- | --- | ---: |
| 91a4d90, `deleteAll()` | 2 357 snapshot'ів, 471 400 юнітів | 105,34 с |
| 43274bf, масові `DELETE` | 2 191 snapshot, 438 200 юнітів | 13,57 с |
| f9e8c4c, `TRUNCATE` | 2 981 snapshot, 596 200 юнітів | 0,03 с |

## Висновки

- Під навантаженням 410 запитів/с брокер відповідає без помилок; 99% запитів виконуються швидше ніж 35 мс.
- Пам'ять контейнера backend стабільна і тримається в межах ліміту, витоків за 2 хвилини безперервного бою не виявлено (NFR-6).
- Час скидання більше не залежить від тривалості бою (FR-8).
- Затримку другого ходу визначає запис snapshot'а. Якщо симуляторів стане більше, `snapshot-interval` можна збільшити без зміни коду.
